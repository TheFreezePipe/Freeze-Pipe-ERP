## 1. Inventory data model today

**product_skus** (baseline L3208): `id, sku (text, unique key), product_name, upc_code (text, nullable), category ('fillable'|'non_fillable'), display_category, retail_price, standard_quantity_per_carton (int, default 1), abc_classification (A/B/C), monthly_demand, is_active, archived_at/by/reason, row_version`. There are NO weight, dimension, barcode-symbology, or bin/default-location columns. `upc_code` exists but nothing in `src/` reads it for scanning. Views `product_skus_active`, `product_boms_active`. Trigger `seed_inventory_level_for_new_sku` (migration `20260603000001`) inserts a zero-stock `inventory_levels` row at Main Warehouse for each new SKU.

**inventory_levels** (baseline L3012; `database.types.ts` L957): one row per (sku_id, location_id), `UNIQUE (sku_id, location_id)` (baseline L3806). Stock is stored as FIVE lifecycle buckets per row, not a single quantity: `warehouse_raw`, `warehouse_prefilled_raw` (added `20260506000002`), `warehouse_in_production`, `warehouse_finished`, `warehouse_other`, plus `row_version`, `last_synced_at`. CHECK >= 0 on every bucket EXCEPT `warehouse_finished`, whose non-negative check was dropped (`20260505000002`) so oversells go negative by policy. Views: `inventory_levels_default` (rows at the `is_default` location), `inventory_totals_by_sku` (sum across locations + `location_count`).

**Effective reality: single-location.** The `location_id` column is plumbed but in practice every row is at Main Warehouse id `00000000-0000-0000-0000-000000000100` (trigger comment, migration `20260603000001`: "all existing inventory_levels rows live there; Nancy Facility (…301) intentionally has none"). Most writers address rows by `sku_id` only and would update every location's row or fail an "expected 1 row" check: `rpc_cycle_count`/`rpc_bulk_cycle_count` (`WHERE sku_id = $2`), `rpc_apply_shipstation_sale` + `shipstation_credit_pair` (raises if row count <> 1; `20260921000001` L202-230), `_freight_credit_units` (`20260722000001` L316). Only `rpc_log_task_completion` is location-aware (`p_location_id`, defaults to `_default_location_id()`, baseline L1550). Frontend `useInventoryBySku` uses `.single()` (src/lib/hooks/use-inventory.ts L34-45), assuming one row per SKU.

**locations** (baseline L3036): `id, code, name, location_type CHECK IN ('warehouse','three_pl','supplier_warehouse','store'), address_*, country, is_default, is_active, owner_supplier_id, row_version`. It is a site-level table (warehouses / 3PL / supplier facilities), NOT bins or shelves. No hierarchy, zone, aisle, bin, or coordinates. Rows are not in migrations/seed; documented rows: Main Warehouse (`...0100`, default) and Nancy facility `NANCY-DOCK` (`...0301`, `supplier_warehouse`) per CLAUDE.md. Actual prod row count is not determinable from the repo. RLS: authenticated read; admin/manager manage; suppliers read their own (`owner_supplier_id`). No UI manages locations (frontend uses `location_id` only in aggregates/retail-value code).

**inventory_transactions** (baseline L3103): append-only ledger. Columns: `id, seq (identity, added 20260601000001), sku_id, transaction_type (free text, no CHECK), quantity, field_affected, movement_kind, from_field, to_field, reference_id, reference_type, notes, performed_by (uuid NOT NULL FK profiles), created_at, row_hash, prev_hash, actor_ip, actor_user_agent`. NO location_id column. `movement_kind` CHECK: `net_change, category_move, metadata, write_off` (widened `20260618000006`). `reference_type` CHECK allowlist: `product_sku, task_log, freight_shipment, factory_order, shipstation_order, profile` (baseline; never widened). `transaction_type` values seen in code: `order_shipped`, `task_logged`, `cycle_count`, `freight_delivered`, `shipstation_oversell_warning`, `shipstation_ledger_rebase`, `shipstation_pre_bootstrap_skip`, `shipstation_absorbed_by_count`, `factory_order_shipped`. Sign convention: stored signed, except `write_off` stored positive (`src/lib/ledger-sign.ts`). Immutability: triggers block UPDATE/DELETE (`block_audit_mutation`); `audit_hash_chain` BEFORE INSERT computes sha256 `row_hash` chained via `prev_hash` under an advisory lock ordered by `seq` (`20260601000001`, `20260602000001/2`); nightly `verify_audit_chain()` cron with checkpoint in `audit_chain_config`. Separate `audit_logs` table (baseline L2802: `actor_id, action, target_table, target_id, details jsonb`) for non-ledger events.

**product_boms** (baseline L3156): `parent_sku_id, component_sku_id, component_type ('produced'|'consumable_inventory'), units_per_parent, assembled_at_supplier_id, component_location_id, effective_from/until`. Models factory assembly (e.g. Nancy compound SKUs containing YX parts), with a cycle check. It is not a sales kit/bundle definition and nothing in the ShipStation path explodes it.

**Reservation/allocation:** none for customer orders. `src/lib/allocation.ts` + migration `20260727000001` use "allocated" only for factory-order components planned into a parent factory order (valuation netting). ShipStation orders deduct `warehouse_finished` directly with no reserved/available split.

**Cycle counts / adjustments:** `rpc_cycle_count(p_sku_id, p_field, p_delta, p_reason, p_notes, p_actor_id)` and `rpc_bulk_cycle_count(p_adjustments jsonb, ...)` (latest `20260511000002`) apply signed deltas per bucket, write `transaction_type='cycle_count'`. Reasons in UI: `breakage|mispick|theft|receiving_error|other` (`use-inventory.ts` L11-13). Materials have their own `rpc_bulk_material_cycle_count`. Breakage via task type `breakage` (write_off of finished).

## 2. Freight / receiving

Tables: `freight_shipments` (baseline L2964; status CHECK includes pending, on_the_water, high_risk, cleared_customs, tracking, delivered, later out_for_delivery; `total_cartons`, carrier piece counts, `receipt_confirmed_at/by`, `closed_short_at/reason`), `freight_line_items` (L2937; `sku_id` now nullable for non-catalog lines, `quantity` = left factory, `quantity_received` rollup, `quantity_prefilled`, `source_factory_order_item_id`), and from `20260722000001`: `freight_carton_groups` (L23: `carton_qty, received_cartons, notes, sort_order`), `freight_carton_group_skus` (L35: `carton_group_id, sku_id, units_total, pre_filled`; mixed cartons = multiple rows), `freight_receipts` (L52: append-only event log with `carton_group_id, sku_id, cartons, units, received_by, received_at, note`).

A "carton group" is a COUNT of identical cartons (e.g. 40 cartons of the same content), not individual carton records; there is no carton id, barcode, license plate, or per-carton row. Groups are created client-side in `src/pages/freight/FreightNew.tsx` L655-700 (non-atomic multi-insert after the shipment). Supplier-created shipments come via `rpc_supplier_create_freight_shipment`.

`rpc_record_freight_receipt(p_shipment_id, p_entries jsonb, p_actor_id)` (`20260722000001` L109-314): admin/manager (or system actor) only; entries are `{carton_group_id, cartons}` (tap-per-carton; negative = correction) or `{line_item_id, units}` (legacy). Carton taps convert to per-SKU units by cumulative rounding `round(units_total*r/carton_qty)`, bump `quantity_received`, write `freight_receipts`, then call `_freight_credit_units` which credits ONE bucket per SKU: non_fillable -> `warehouse_finished`; fillable -> `warehouse_prefilled_raw` if `pre_filled` else `warehouse_raw`, ledger row `transaction_type='freight_delivered'`, `reference_type='freight_shipment'`. When all catalog lines are received the shipment flips to `delivered` and `receipt_confirmed_at` is stamped. `rpc_close_freight_short` writes shortage variances. `rpc_apply_freight_delivery` is the receive-all wrapper (`20260908000001` squares carton counters).

**Cartons do not persist as inventory containers.** After check-in they dissolve into unit counts in a bucket; `received_cartons` is just a counter on the plan. Master-carton identity, contents-per-carton beyond `standard_quantity_per_carton`, and any putaway location are not recorded. Receiving UI: dock banner + steppers in `src/pages/freight/FreightDetail.tsx` + `components/freight/ShipmentManifest.tsx`; predicate `src/lib/freight/receiving.ts`.

## 3. ShipStation integration today

Docs: `docs/SHIPSTATION_INTEGRATION.md` (runbook). API: ShipStation V1 (`https://ssapi.shipstation.com`, `/orders` with `modifyDateStart/End`, `pageSize`, `page`), HTTP Basic with `SHIPSTATION_API_KEY:SHIPSTATION_API_SECRET` (Deno env secrets, never in `src/`). Only reads; the code never writes back to ShipStation (no PUT/POST of orders, labels, or tags).

**Edge functions**
- `shipstation-webhook/index.ts` (410 lines; deploy `--no-verify-jwt`): auth = `?s=` secret equal to `SHIPSTATION_WEBHOOK_SECRET` (L98-102) plus optional `SHIPSTATION_IP_ALLOWLIST`. Payload only needs `resource_url` and `resource_type`; no per-event branching (any registered event is treated the same; doc registers `ITEM_SHIP_NOTIFY`, optionally `ORDER_NOTIFY`). Idempotency key `event_id = resource_url:resource_type:sha256(body)` with UNIQUE index in `shipstation_webhook_events`; duplicate -> 200. Event row persisted first, then it GETs `resource_url` and expects either `{orders:[...]}` or a single order object (no `shipments` shape handling), upserts `shipstation_orders` (full payload in `raw_payload` jsonb), rebuilds `shipstation_order_items` only while `inventory_applied_at IS NULL`, resolves SKUs via `_shared/shipstation-resolve.ts`, then calls `rpc_apply_shipstation_sale` with fixed system actor `00000000-0000-0000-0000-000000000001`. Retry wrapper: 4 attempts, 250ms*2^n on 5xx/429/network (no `X-Rate-Limit-*` header handling). Failures leave `processed_at NULL` + `processing_error`, still return 200.
- `shipstation-reconcile/index.ts` (423 lines; Bearer-required, called by pg_cron `shipstation-reconcile-intraday` every 30 min with vault `service_role_jwt`, plus nightly 03:15 UTC per docs; migration `20260610000001` L206): Stage 1 replays unprocessed events (attempts < 6); Stage 2 pulls a rolling 26h `modifyDate` window (pageSize 50, up to 100 pages), upserts, flags status/total drift into `shipstation_sync_runs`; Stage 2b rebuilds lines from `raw_payload`; Stage 3 calls the RPC for up to 500 unapplied `shipped|awaiting_shipment` orders. Retry 500ms*2^n.
- `shipstation-backfill/index.ts` (one-time sales-history pull into `sales_backfill_raw`; pageSize 500, 200ms sleep, comment cites 40 req/min limit, 429 -> sleep 2s).
- `_shared/shipstation-resolve.ts`: order of resolution = alias in `shipstation_sku_handling` -> case-insensitive `product_skus.sku` -> prefix rule on hyphenated codes (shortest prefix first, auto-registers an alias with note "auto: prefix rule") -> NULL (unresolved, blocks stamp). Empty SKU or qty<=0 skipped; non-inventory codes dropped.

**Tables:** `shipstation_orders` (baseline L3350: `shipstation_order_id bigint UNIQUE, order_number, order_status (free text), order_date, ship_date, customer_email/name, store_id/name, *_cents, inventory_applied_at, inventory_apply_attempts, inventory_apply_error, last_seen_via ('webhook'|'api_pull'|'manual'), raw_payload`; `box_applied_at` added `20260609000004`), `shipstation_order_items` (L3331: `shipstation_line_item_id, sku_code, sku_id (nullable), quantity, unit_price_cents`; deleted + re-inserted on re-ingest), `shipstation_sku_handling` (alias / `is_non_inventory`, PK `sku_code`), `shipstation_webhook_events`, `shipstation_sync_runs` (run_type `webhook_replay|nightly_reconcile|backfill`), `shipstation_order_discounts` (parsed by trigger from payload), views `shipstation_unresolved_skus`, `shipstation_unresolved_skus_pending`, `shipstation_unmatched_boxes`. Ledger "rebase" is not a table: it is `inventory_transactions` rows of type `shipstation_ledger_rebase` / `shipstation_absorbed_by_count` (metadata, no stock move; `20260921000001`). Retention: processed events >30d and sync runs >90d purged by cron (`20260702000001`). Known store ids: 229438 main Shopify, 229435 Manual Orders, 383716 second Shopify (`20261013000001`). Quirk: `orderDate` is a Pacific wall-clock stored as UTC; `fn_ss_et` corrects.

**Inventory deduction (`rpc_apply_shipstation_sale`, latest `20260921000001` L244-594, SECURITY DEFINER, granted to anon/authenticated/service_role L589):** gate is order STATUS, not the ship event: both `shipped` and `awaiting_shipment` deduct (webhook L232-237; reconcile Stage 3 filters the same). `on_hold`, `awaiting_payment`, `cancelled` are stored but skipped. So deduction today happens at order-commit time, before physical shipping, by owner design (oversell workflow). Idempotency is ledger-derived: per (order, sku) `delta = lines - net(order_shipped + rebase rows)`; positive deducts from `warehouse_finished` (writes oversell warning if short, still decrements), negative credits back. Order row `FOR UPDATE` serializes callers. Pre-bootstrap cutoff 2026-05-05 skipped. Unresolved codes park only that line; cancelled orders owe 0 but edge functions never call the RPC for them, so cancellations after deduction are NOT auto-credited (open owner decision). Boxes: `rpc_apply_shipstation_boxes` / trigger `_apply_box_for_shipped_order` (`20260610000001`) decrement a `materials` box by matching `raw_payload.dimensions` L x W x H when status becomes `shipped`.

**Picking/packing state today: none.** No per-line picked/packed quantity, no pick task, no bin, no scan confirmation, no tote/wave concept; the only fulfilment flags are `inventory_applied_at` and `box_applied_at`. Ship date and package dimensions arrive only through ShipStation after labeling.

## 4. Manufacturing / materials flows that move stock

`rpc_log_task_completion` (baseline L1550; crew `Workspace` page `src/pages/manufacturing/Workspace.tsx`) with task types via `_task_type_movement` (latest `20260506000002`): `emptying` raw -> in_production; `filling_capping` no bucket move; `rtsing` in_production -> finished; `prefilled_rtsing` prefilled_raw -> finished; `breakage` finished -> write-off. Inserts `task_logs` row + `inventory_transactions` (`task_logged`, `category_move`, reference `task_log`). It rejects with `insufficient_source_stock` if the source bucket is short. Trigger `trg_consume_materials_on_fill` (AFTER INSERT on `task_logs`, `20260827000003`) deducts glycerin etc. per `sku_material_consumption` into `material_transactions` (`task_consumption`, floored `material_inventory_levels`). Materials family (`20260526000001`): `materials, material_inventory_levels, material_transactions, sku_material_consumption`, separate ledger. Finished goods thus come from `rtsing` (manufacturing) and non-fillable receiving, and leave through ShipStation deduction; a pick module would consume `warehouse_finished` and contend for the same rows. Factory orders and freight in transit are derived quantities, not warehouse stock.

## 7. Integration hooks (OPTIONS, not decisions)

1. **Location-aware stock.** (a) Reuse `inventory_levels (sku_id, location_id)`: `locations` is already a FK target and unique pair exists, but `location_type` is site-level, the five lifecycle buckets are columns, and the writers above are SKU-keyed, so bin-level rows would need those RPCs and `useInventoryBySku` changed first. (b) Add a new table (e.g. `inventory_balances` keyed by sku_id + bin/location_id + lifecycle bucket or just finished stock) and keep `inventory_levels.warehouse_finished` as the roll-up; this leaves existing RPCs, `inventory_totals_by_sku`, retail-value snapshots, and the reporting API untouched. (c) Add a child `bins`/`warehouse_slots` table referencing `locations.id` (or extend `locations` with a parent_id/zone/coordinate set) for the map geometry. Either way `inventory_transactions` has no location column, so per-location history needs a new column or a sibling ledger; the hash chain and `reference_type` CHECK allowlist must be extended consciously.
2. **Receiving putaway.** `rpc_record_freight_receipt` / `_freight_credit_units` are the single credit point; carton groups are count-only. Options: optional `location/bin` argument on each receipt entry written to a new putaway row; or introduce persistent carton/pallet rows created from `freight_carton_groups` at check-in (today they dissolve). `freight_receipts` already logs who/when/how many and could carry a destination.
3. **Pick-task creation.** Natural attach point is where `shipstation_orders`/`shipstation_order_items` rows are upserted and SKU-resolved (`shipstation-webhook` `upsertOrder`, `shipstation-reconcile` `upsertAndReconcile`, both calling `_shared/shipstation-resolve.ts`) or a DB trigger on `shipstation_order_items`. Resolved `sku_id`, `quantity`, order status and full `raw_payload` are available; BOM explosion is not done today. Pick tables would be new (`pick_tasks`/`pick_lines`) with status, assignee (`profiles.id`), bin, picked qty. `awaiting_shipment` is the status that denotes "ready to pick".
4. **Ship-confirm / consumption.** Today stock already leaves `warehouse_finished` at `awaiting_shipment`/`shipped` via `rpc_apply_shipstation_sale`; there is no reserved bucket. Options: (a) leave deduction as is and have picking draw down bin balances only (balances reconcile to the roll-up); (b) move bin consumption to pick confirmation and make `rpc_apply_shipstation_sale` target = picked lines; (c) add reservation columns. Any change must keep its ledger-derived idempotency rule and the oversell/negative-allowed policy, and coexist with the `box_applied_at` box trigger (fires on status `shipped`) and with `rtsing`/`prefilled_rtsing` crediting `warehouse_finished`.
5. **UI.** New routes would go in `App.tsx` under `RequireRole` (warehouse staff are role `user`, currently landing on Workspace), a Sidebar group, hooks in `src/lib/hooks`, RPCs prefixed `rpc_`. Requirements with no existing precedent: camera permission (Permissions-Policy), scanner library, PWA/offline, label printing, map rendering library, Supabase Realtime subscriptions, a table/combobox primitive.
