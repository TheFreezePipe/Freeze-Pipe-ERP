# Own the pick, let ShipStation print

The viable version of this module is one in which **the Freeze Pipe ERP owns every warehouse decision (where stock sits, who picks what, which tote it goes in, whether the box is right) and ShipStation keeps only the two jobs it already does well: receiving orders from Shopify and printing carrier labels.** That split is forced, not chosen. ShipStation's own Pick to Tote is a Premium-plan feature (from **$349.99/month**) that works only if ShipStation becomes the inventory and bin-location system of record, it exposes no pick, pack or tote state through any API or webhook, and its Pick to Light is an unreleased, cart-only, closed feature ([ShipStation plans](https://help.shipstation.com/hc/en-us/articles/38800795536027-Learn-About-ShipStation-Subscription-Plans); [V2 OpenAPI bundle](https://docs.shipstation.com/_bundle/apis/@shipstation-v2/openapi.json); [ShipStation blog](https://www.shipstation.com/blog/warehouse-picking-packing/)). A 3D map that tracks every unit and carton, a route-guided picker, and home-built lights are therefore impossible on top of ShipStation and must be built inside the ERP, which today has none of the needed foundations: stock is one row per SKU at a single site-level "Main Warehouse", there are no bins, reservations, pick/pack state, Realtime subscriptions, installable mobile app, barcode scanning or printing code, and the Vercel config actively blocks camera access (`vercel.json`, `supabase/migrations/20260504000001_baseline_schema_from_staging.sql`). The full scope is four layers: a location master with rack templates, bin barcodes and a physical-balance ledger that reconciles nightly to the existing SKU-level ledger (the current sales deduction at `awaiting_shipment` stays untouched); a phone-based progressive web app that builds cluster-picking carts on demand, scans location, item and tote, and routes pickers by a serpentine walk order first and an exact shortest path later; a pack station that verifies by scan and hands the order to ShipStation's Scan to Print with an order-number barcode (zero label-API risk) before graduating to ERP-purchased ZPL labels; and a pick-to-light layer that starts as cart-slot "put-to-light" on roughly **$300-$1,000 of ESP32/WLED hardware** or a **$5,000 Voodoo Robotics starter kit**, never as a dependency the picker cannot work without ([WLED JSON API](https://kno.wled.ge/interfaces/json-api/); [Voodoo pricing](https://voodoorobotics.com/pricing/)). The React 19.2 / Vite 8 stack already supports the current 3D libraries (react-three-fiber 9, drei 10), so the one technical blocker the earlier brief assumed does not exist. Cash outlay for phases 1-3 is small (a label printer, two or three Bluetooth scanners, totes and labels, about $9/month of print service); the real cost is engineering time and the owner's decisions on inventory ownership, label hand-off, and how far to go with per-carton tracking.

## ShipStation cannot be the picking brain, so the ERP must be

The strongest evidence in this research is negative: everything the owner wants is on the far side of a wall ShipStation does not let anyone cross. ShipStation's warehouse features are real and reasonably priced. On Standard (from **$29.99/month**, 10 users) the account gets API access, webhooks, Mobile Picking with barcode confirmation and the Scan page for verify-and-print; Premium (from **$349.99/month** at 50 shipments, **$599.99** at 1,000, **$799.99** at 5,000) adds Pick to Tote, Scan to Receive, purchase orders, transfer orders and Cubiscan dimensioning ([ShipStation pricing](https://www.shipstation.com/pricing/); [ShipStation plans](https://help.shipstation.com/hc/en-us/articles/38800795536027-Learn-About-ShipStation-Subscription-Plans)). Pick to Tote is genuine cluster picking: the picker declares how many totes are on the cart, ShipStation assigns that many orders first-in-first-out, and the picker scans location (skippable), scans an empty tote to bind it to an order, then scans each item into that tote ([Pick Using Batches](https://help.shipstation.com/hc/en-us/articles/49132678007451-Pick-Using-Batches)). But its prerequisites are "Manage Inventory in ShipStation" and "Manage Warehouse Locations", meaning ShipStation must be the stock-of-record and the bin master ([Pick Using Batches](https://help.shipstation.com/hc/en-us/articles/49132678007451-Pick-Using-Batches)). Its "route" is a sort of the pick list by quantity, name, SKU or location string, nothing more ([Configure Mobile Picking](https://help.shipstation.com/hc/en-us/articles/49132708104219-Configure-Mobile-Picking)). Partial picks are not supported, labels can only be created after picking, and the Ready to Pick / Picking / Picked statuses "are visible in both the mobile and web apps" and nowhere else ([Introduction to Mobile Picking](https://help.shipstation.com/hc/en-us/articles/49132708040347-Introduction-to-Mobile-Picking)).

The API confirms the blindness. A text search of the entire V2 OpenAPI bundle finds no pick-list endpoint, no picking-status field and no packing-verification field; the `/v2/totes` endpoint added in February 2026 is master data only (name, barcode, warehouse) with no order assignment or contents; the webhook event list (`batch`, `label_created_v2`, `shipment_created_v2`, `fulfillment_shipped_v2`, `track_event_v2` and a few others) carries no pick, pack, tote or verify events ([V2 OpenAPI bundle](https://docs.shipstation.com/_bundle/apis/@shipstation-v2/openapi.json); [V2 release notes](https://docs.shipstation.com/apis/release-notes.md)). An external system can pre-create totes, write locations and stock, assign users to label batches and download batch packing slips, but it cannot mark an order Ready to Pick, cannot see which tote holds which order, and cannot learn about a short pick until a label is created. A ShipStation community thread (login-gated, seen only via search summary) reported exactly that pain: no reporting on which tote holds which order, with notes-in-bins as the workaround ([community thread](https://community.shipstation.com/t5/ShipStation-Features/Mobile-Picking-Challenges-Opportunities/td-p/29746)). Pick to Light is described in a June 2026 blog post as "coming soon" on Premium, as LED devices mounted on tote slots of the picking cart that light when the picker scans at a bin; no hardware, price, release date or API has been published ([ShipStation blog](https://www.shipstation.com/blog/warehouse-picking-packing/)). For a module whose purpose is a map of every unit, route guidance and lights the team drives with its own software, that is three closed doors.

The position this report takes is therefore the "ERP-native" pattern: **the ERP is the inventory owner and the picking engine; ShipStation Inventory stays switched off; ShipStation remains the order inbox, the label and rate engine, and the system that tells Shopify an order shipped.** This is the same shape as the integrations that stay on ShipStation rather than replace it: SkuVault pulls orders by tag, drives pick sessions in its own app and prints labels using ShipStation as the carrier engine, inFlow pushes fully picked orders to ShipStation as pending shipments and pulls tracking back, and SKULabs documents both "ShipStation prints, we pick" and "we pick and pack, then scan the ShipStation order barcode to print" patterns ([SkuVault partner page](https://www.shipstation.com/en-ca/partners/skuvault-core.md); [inFlow support](https://www.inflowinventory.com/support/cloud/connecting-inflow-to-shipstation); [SKULabs help](https://www.skulabs.com/help/en/articles/8240397-how-to-pick-pack-and-ship-using-both-skulabs-and-shipstation)). ShipStation itself documents the two WMS patterns ("Shipping": WMS picks, ShipStation labels; "Pick-Pack": ShipStation syncs orders to the WMS) and advises choosing one inventory owner to avoid double entry ([ShipStation WMS page](https://www.shipstation.com/fulfillment/warehouse-management/)). The alternative, running Premium mobile picking and mirroring stock back by polling `/v2/inventory`, is the fastest thing to deploy for a 2-5 person team, but it means the ERP learns about an order only when the label exists, two location masters and two tote registries drift, and no map, route optimizer or custom light can ever be layered on. That path is worth naming as the fallback if the owner decides the custom module is not worth building; it is not a base to build on.

"Seamless, real time" with ShipStation then has a precise meaning. Orders arrive as they do today through the V1 webhook and the 30-minute reconcile (`supabase/functions/shipstation-webhook/index.ts`, `shipstation-reconcile/index.ts`), with the poll interval tightened to a few minutes because V1 webhooks are thin pings with no signature and no documented retry, and ORDER_NOTIFY fires on import, not on later edits or cancellations ([V1 webhook model](https://www.shipstation.com/docs/api/models/webhook/); [Hookdeck guide](https://hookdeck.com/webhooks/platforms/guide-to-shipstation-webhooks-features-and-best-practices.md)). The V1 budget is **40 requests per minute** per key pair with `X-Rate-Limit-*` headers and 429 on excess, so the picker's phone must never call ShipStation; it reads and writes only Supabase, and ShipStation calls are queued background work ([V1 requirements](https://www.shipstation.com/docs/api/requirements/)). Status flows the other way through account tags applied with `POST /orders/addtag` (for example ERP-PICKING, ERP-PICKED, ERP-EXCEPTION), which are visible and filterable in ShipStation and usable by its automation rules without touching order data; `holduntil`/`restorefromhold` can additionally park an order while it is on a cart so nobody prints a label mid-pick ([V1 Add Tag](https://www.shipstation.com/docs/api/orders/add-tag/)). Full-order rewrites through `createorder` should be avoided: the call has no partial update, requires the entire resource, and only works on open orders, so pushing bin locations into ShipStation's `warehouseLocation` field is both risky and unnecessary once the ERP prints its own pick guidance ([V1 Create/Update Order](https://www.shipstation.com/docs/api/orders/create-update-order/)). V1 is officially deprecated with no removal date, and V2 (ShipEngine-based, 200 requests per minute, `API-Key` header) still has no full sales-order model, so every ShipStation call belongs behind one adapter module that can be re-pointed when V1 goes away ([V2 authentication](https://docs.shipstation.com/authentication); [V2 rate limits](https://docs.shipstation.com/rate-limits); [V2 getting started](https://docs.shipstation.com/getting-started)).

The label hand-off is the one place the two systems must physically meet, and there are two workable designs. The low-risk design uses ShipStation's own Scan page: Scan to Print opens a shipment when the packer scans "a Scan to View Barcode or an order number barcode", weighs via a USB scale through ShipStation Connect, and prints ([Verify & Print with Barcode Scan](https://help.shipstation.com/hc/en-us/articles/360031021831-Verify-Print-Shipments-with-Barcode-Scan)). The ERP's pack screen can render that order-number barcode (or print it on the tote label), so after ERP-side verification the packer scans the ERP screen into ShipStation and the label prints with no API write at all. The higher-integration design has the ERP purchase the label itself through `POST /v2/labels/shipment/{shipment_id}` (PDF, PNG or ZPL output, with `label_download_type: inline`) or V1 `createlabelfororder` (base64 PDF), and push it to a thermal printer through PrintNode ([V2 Create Labels](https://docs.shipstation.com/create-labels); [V1 Create Label for Order](https://www.shipstation.com/docs/api/orders/create-label/)). Two things about the second design are unverified in official documentation and must be proved in a test account before committing: whether a V2 label on the order's backing shipment marks the ShipStation order shipped and notifies Shopify, and whether API labels count against the plan's shipment quota (the working assumption is yes to both). This report recommends shipping the first design in phase 3 and treating the second as an upgrade once the pack station is stable.

## Viability means table stakes plus three differentiators, not everything

Benchmarking fourteen SMB products shows a stable floor of features that every serious pick-and-pack system provides, and the custom module is only viable if it clears that floor; otherwise the team would be better served by a **$350-$1,000/month** subscription. The floor is scan-confirmed picking on a phone or scanner, a bin or location per SKU, batch picking with either a tote per order or one shared pile, scan-to-verify at packing that blocks the label until items match, inventory sync to channels, cycle counts, receiving, returns, and basic per-picker reporting ([Veeqo digital picking](https://help.veeqo.com/en/articles/8306650-digital-picking-overview); [ShipHero mobile picking interface](https://software-help.shiphero.com/hc/en-us/articles/40363495768077); [Zenventory pricing](https://www.zenventory.com/pricing)). The spend this module displaces is real but modest: ShipStation Standard at 1,000 shipments is **$149.99/month** versus Premium **$599.99**; SKUSavvy prices by order at about **$324/month** at 1,000 orders plus **$2,750** onboarding; Zenventory is **$499/month plus $1,000 setup**; Finale's Growth plan with the barcode module is **$799/month**; ShipHero is reported around **$1,995/month plus $150 per extra user**; Peoplevox starts at **$2,050/month** platform fee plus users and roughly **$10,000** implementation ([ShipStation pricing](https://www.shipstation.com/pricing/); [SKUSavvy pricing](https://skusavvy.com/skusavvy-pricing); [Zenventory pricing](https://www.zenventory.com/pricing); [Finale pricing](https://www.finaleinventory.com/pricing/); [Eightx ShipHero](https://eightx.co/blog/compare/how-much-does-shiphero-cost); [Peoplevox pricing](https://www.peoplevox.com/pvx-pricing/)). Several of those (ShipHero, Veeqo, Packiyo) are shipping platforms that replace ShipStation outright; the ERP-style products that keep ShipStation (inFlow, Zenventory, SkuVault, Cin7) are the right comparators, and the custom module is architecturally one of them.

What justifies building rather than buying is a short list of things none of the comparators sells at this price. Only SKUSavvy markets a visual warehouse map, and its page describes locating bins, filled-versus-empty views, activity heatmaps for slotting, pick routes drawn on the map, count paths and map-guided putaway, with "3D" appearing mainly in image alt text and a separate "3D palletization" feature ([SKUSavvy warehouse mapping](https://www.skusavvy.com/warehouse-mapping-software); [SKUSavvy visual inventory](https://skusavvy.com/visual-inventory-management-system)). Competitors' "optimized pick path" is almost always a sort by location code: ShipHero computes the route once at batch creation using pickable-bin rules, pick priority and then location-name order, and warns that inconsistent names produce zig-zag routes; Veeqo lists items in ascending bin order and tells users to zero-pad codes so they sort as text ([ShipHero pick path](https://software-help.shiphero.com/hc/en-us/articles/46894155095565); [Veeqo digital picking](https://help.veeqo.com/en/articles/8306650-digital-picking-overview)). Unit and master-carton positions are beyond what most SMB products track at all; they track bin quantities. And cart-mounted lights exist today only as ShipHero's feature-flagged kit requiring its "Attainable Automation Kit", and tomorrow as ShipStation's announcement ([ShipHero pick-to-light](https://software-help.shiphero.com/hc/en-us/articles/36575614089741-How-to-Use-ShipHero-s-Pick-to-Light)).

The scope decision, then, is to build the floor plainly and spend ambition on three differentiators: a map with unit and carton addresses, true route and batch optimization, and a tote-slot interface that lights can attach to later. The table below is the recommended scope cut.

Two cautions about the differentiators. First, the operational value of the map is delivered by the 2D views; 3D is an owner-facing overview and a presentation asset, which is why the most comparable small-ecommerce product (Skustack Visualize) ships a 2D grid with bin cards, search highlighting and numbered pick-path overlays and no 3D at all ([Sellercloud Visualize](https://lms.sellercloud.com/courses/skustack-and-skustack-lens/lessons/visualize-module-workflow/)). Second, the measurable gain from exact routing over a sensible serpentine walk order is smallest exactly where Freeze Pipe lives (short pick lists, one small block); the academic literature's 6-39% gaps between heuristics and optimal routes come from scattered, longer lists, while most of the saving at this scale comes from batching and slotting ([Petersen 1997](https://iaorifors.com/paper/23908); [RePEc thesis](https://ideas.repec.org/p/dar/wpaper/119000.html); [Petersen & Aase 2004](https://www.iaorifors.com/paper/47394)). The module should still implement exact routing because it is a few hundred lines of TypeScript, but the roadmap should not wait for it.

## Give every unit and carton an address without breaking today's ledger

Today's data model is a single-site, bucketed count: `inventory_levels` has one row per (sku, location) with a unique pair, every row sits at Main Warehouse id `…0100`, and stock is five lifecycle buckets (`warehouse_raw`, `warehouse_prefilled_raw`, `warehouse_in_production`, `warehouse_finished`, `warehouse_other`) rather than a quantity ([baseline migration](supabase/migrations/20260504000001_baseline_schema_from_staging.sql); `supabase/migrations/20260603000001_seed_inventory_on_sku_create.sql`). `locations` is a site table (warehouse, 3PL, supplier warehouse, store) with no hierarchy, zone, bin or coordinates, and most writers (`rpc_cycle_count`, `rpc_apply_shipstation_sale`, `_freight_credit_units`, the frontend's `useInventoryBySku().single()`) address rows by SKU only and would misbehave if a second location row appeared (`supabase/migrations/20260921000001_shipstation_apply_once.sql`; `src/lib/hooks/use-inventory.ts`). Receiving is carton-native but transient: `freight_carton_groups` is a count of identical cartons, `rpc_record_freight_receipt` converts carton taps into per-SKU units and credits one bucket, and the cartons then dissolve; there is no carton id, barcode or putaway destination (`supabase/migrations/20260722000001_partial_freight_receiving.sql`). The audit ledger `inventory_transactions` has no location column, is hash-chained and immutable, and its `reference_type` CHECK allowlist would need a migration before a pick task could be referenced (`supabase/migrations/20260601000001_audit_chain_seq_fix.sql`).

The recommended design adds a physical layer beside the existing SKU layer rather than rewriting it. The industry consensus for inventory-at-location systems is an append-only movement ledger as source of truth plus a maintained balance table keyed by item, location and container, with on-hand, allocated and available, updated atomically in one transaction ([Cleverence inventory schema](https://www.cleverence.com/amp/articles/for-business/inventory-control-database-schema-4721/); [Cleverence SQL inventory](https://www.cleverence.com/articles/for-business/how-to-create-an-inventory-database-in-sql-4732/)). Applied here: new tables `wh_locations` (bins, racks, zones, stations, parented to the existing `locations` site row), `containers` (master cartons, totes, pallets, each with a license-plate barcode), `inventory_balances` (sku × bin × optional container) and `inventory_movements` (every putaway, move, case-break, pick, pack, ship, count), all written through `SECURITY DEFINER` RPCs that lock the balance row and insert the movement in one transaction, matching the ERP's existing `rpc_*`, JSONB envelope and `FOR UPDATE` conventions (`CLAUDE.md`; `src/lib/query-client.ts`). The existing `inventory_levels.warehouse_finished` stays the SKU-level roll-up that the rest of the ERP, the retail-value snapshots and the reporting API already read. Physical moves between bins change no SKU total and therefore write nothing to the hash-chained `inventory_transactions`; only events that change a SKU total (receipt, count variance, write-off, sale) touch it, exactly as today. A nightly job checks the identity **physical on-hand in all pickable, reserve and tote locations minus units allocated to open `awaiting_shipment` orders equals `warehouse_finished`**, and files any mismatch as a count task. That single rule lets the owner keep the deliberate "deduct at order commit, allow negative finished stock" policy encoded in `rpc_apply_shipstation_sale` while gaining a true picture of where units physically are (`supabase/migrations/20260505000002_allow_negative_finished_inventory.sql`).

Master cartons become first-class records at the moment they are received. In WMS practice each pallet or carton is a license plate number (LPN) that ties SKU, quantity, lot and current location to the container, and inventory moves by moving the LPN; master cases live in reserve locations and are "broken" to feed forward pick faces, with min/max rules that move whole cartons and fill the face to its maximum ([Racklify license plates](https://racklify.com/encyclopedia/wms-and-erp-pallet-management-tracking-license-plates-and-tier-locations/); [Racklify case break](https://racklify.com/encyclopedia/case-level-picking-vs-breaking-bulk-warehouse-strategies-for-master-carton-handling/); [Racklify reserve storage](https://racklify.com/encyclopedia/reserve-storage-location-definition-and-role-in-fulfillment/)). The ERP's carton groups map onto this directly: at check-in `rpc_record_freight_receipt` already knows the group, SKU mix and units per carton, so it can mint one `containers` row per carton (type `master_carton`, contents from `freight_carton_group_skus`, lot = the freight shipment), print an LPN label, and the putaway step becomes "scan carton, scan shelf". Mixed-SKU cartons work because contents are a child table, not columns. A case break is an explicit movement that decrements the carton's contents and increments loose stock at the pick face; when the carton hits zero it is marked consumed, preserving traceability back to the receipt. The owner must decide whether every carton gets its own label or whether a group of identical cartons on one shelf can share one record with a count; per-carton labels are the only way to satisfy "every master carton is allocated to a specific location" literally, at the cost of one label per carton at receipt.

Location naming should be boring and future-proof. Practitioner guidance converges on a fixed-width, zero-padded hierarchy of aisle, bay (section), level and position, with odd bays on one side of the aisle and even on the other, levels counted from the floor up, and labels in Code 128, black on white or yellow, with a check digit the app can ask for to confirm the picker is at the right slot ([We Are The Practitioners](https://www.wearethepractitioners.com/index.php/topics/warehouse-operations/functions-terms/location-numbering-warehouses); [Warehance](https://warehance.com/blog/smart-warehouse-setup-zoning-and-location-naming-that-works); [Cleverence rack numbering](https://www.cleverence.com/articles/for-business/warehouse-rack-numbering-system-4827/)). The same guidance warns never to mix `A-1-1` with `A-01-01` and to start numbering mid-range so the building can grow in either direction ([Warehance](https://warehance.com/blog/smart-warehouse-setup-zoning-and-location-naming-that-works)). Two design choices matter more than the format: keep the printed code (for example `A-03-2-B`) separate from the scanned value (prefixed, so the app knows a scan is a location rather than a UPC or tote without a lookup), and store a separate integer `pick_sequence` so the walking route is data, not baked into label names; a re-layout then rewrites integers, not shelves. For visually similar glass variants, one SKU per pick face and a scan-confirm step are hard rules, and quarantine, damaged and returns areas are modeled as location types whose `is_sellable` flag is false, mirroring OpenBoxes' "hold bins" whose stock is simply not available to pick ([OpenBoxes hold bins](https://openboxes.helpscoutdocs.com/article/67-creating-hold-bins)). SAP EWM keeps XYZ layout coordinates as separate numeric fields from the logical aisle/stack/level address and uses them both to draw its Graphical Warehouse Layout and to compute travel distance; the ERP should do the same, storing millimeter coordinates on racks and derived bin boxes so the renderer and the router never need template math at runtime ([SAP GWL blog](https://groups.community.sap.com/t5/supply-chain-management-blogs-by-members/graphical-warehouse-layout-in-sap-ewm/bc-p/13563953); [SAP creating storage bins](https://learning.sap.com/courses/basic-customizing-in-sap-s-4hana-ewm/creating-storage-bins)).

Digitizing the building is a one-week physical job, not a software problem, and the proven path is template-based. SAP generates bin master data from templates after the aisle/stack/level coding is defined; Skustack detects existing bin-name patterns, lets the user map name segments to hierarchy terms, then places elements on a sized grid; Bartholdi's heat-map tool needs only a spreadsheet grid of unique rack addresses plus a CSV of metrics ([SAP creating storage bins](https://learning.sap.com/courses/basic-customizing-in-sap-s-4hana-ewm/creating-storage-bins); [Sellercloud Visualize](https://lms.sellercloud.com/courses/skustack-and-skustack-lens/lessons/visualize-module-workflow/); [Warehouse Science heat map](https://www.warehouse-science.com/apps/heatmap/index.html)). For Freeze Pipe: measure the footprint, each shelving unit, aisle widths, pack benches and doors in millimeters; define two to four rack templates (a 48-inch five-shelf wire unit with four positions per shelf, a pallet bay, a floor pallet spot, a pack bench) with bays, levels, positions, dimensions and a default location type per level; place instances in a 2D editor with snap and 90-degree rotation; let the system generate codes, barcodes, coordinates and a default serpentine `pick_sequence`; print labels in rack order and walk the building scanning each to verify; then load initial stock by scanning carton or SKU, scanning the location and entering quantity, followed by a full count. Layout versioning (draft versus published) lets a rack move later without corrupting history, and a bin can be deactivated only when empty.

Rendering is the part the earlier brief got wrong, in the ERP's favor. The package manifest pins `react ^19.2.4` and `vite ^8.0.1` (`package.json`), and the current 3D stack requires exactly that: `@react-three/fiber` 9.8.2 has peer `react >=19 <19.4`, `@react-three/drei` 10.7.9 has peer `react ^19` and fiber `^9`, `react-konva` 19.3.2 has peer `react ^19.3.0`, and `three` is at 0.186.1 ([npm @react-three/fiber](https://registry.npmjs.org/@react-three/fiber/latest); [npm @react-three/drei](https://registry.npmjs.org/@react-three/drei/latest); [npm react-konva](https://registry.npmjs.org/react-konva/latest); [npm three](https://registry.npmjs.org/three/latest); [R3F v9 migration guide](https://r3f.docs.pmnd.rs/tutorials/v9-migration-guide)). No pinning to the frozen React-18 lines is needed. The recommended architecture is one data model and three renderers: a top-down 2D floor plan in plain SVG (zero dependency, printable, tappable, trivially themeable in the ERP's dark mode) as the default view, the layout editor and the picker's mini-map; a rack elevation view in SVG (bays × levels grid with contents) when a rack is tapped; and a lazy-loaded react-three-fiber scene on desktop for the owner's 3D requirement. In three.js a few thousand bins are one `InstancedMesh` draw call with per-instance color for occupancy and pick-frequency heatmaps; raycast hits return `instanceId` for click-to-inspect, with the caveat that `instanceColor.needsUpdate` must be set after color changes and raycasting should not run on every mousemove ([three.js forum on instanced raycast](https://discourse.threejs.org/t/change-color-of-instance-mesh-index-on-raycast/38136.md)). A pick route is a drei `<Line>` through aisle waypoints; `frameloop="demand"` and capped device-pixel ratio keep it cheap. Konva is the right choice only if the team wants drag-and-drop in the editor beyond what SVG offers, and it brings canvas memory limits on Mobile Safari that SVG does not ([Konva performance tips](https://konvajs.org/docs/performance/All_Performance_Tips.html)). The features worth copying into the map are search (SKU, LPN, order) that highlights bins; color modes for occupancy versus capacity, stock versus minimum, picks in the last 30 or 90 days, and days since last count; a bin card with image, quantities, cartons and receipt; a numbered pick-path overlay like Skustack's per-picker colors; and drag-a-SKU-to-another-bin in the editor that creates a re-slot task rather than changing data instantly ([Sellercloud Visualize](https://lms.sellercloud.com/courses/skustack-and-skustack-lens/lessons/visualize-module-workflow/); [Mecalux heatmap slotting](https://www.mecalux.com/software/updates/heatmap-slotting)). Slotting itself can start as a SQL view: picks per SKU over 90 days, ABC class, golden-zone levels flagged on locations, and a monthly "A SKUs outside the golden zone / C SKUs inside it" list; class-based storage captures nearly the same savings as batching and is less sensitive to order size, which makes it the cheapest lever after the map exists ([Petersen & Aase 2004](https://www.iaorifors.com/paper/47394); [Cleverence slotting](https://www.cleverence.com/articles/for-business/inventory-slotting-7463/)).

## Guide the picker from a phone: PWA, scans, totes and an exact route

The delivery vehicle should be the existing React app installed to the home screen as a progressive web app, with a native wrapper held in reserve. iOS has steadily closed the gaps that mattered: `getUserMedia` camera access since iOS 13, Screen Wake Lock fully for installed PWAs since 18.4, Web Push for installed apps since 16.4, login cookies copied into the installed app since 17.2, and on iOS 26 any site can be installed as a web app without a manifest ([firt.dev iOS PWA notes](https://firt.dev/notes/pwa-ios/)). What iOS still lacks is the Vibration API, Web Bluetooth/HID/NFC and any background sync, and there are long-standing WebKit reports that a camera stream in standalone mode is dropped on route changes and sometimes re-prompts for permission ([firt.dev](https://firt.dev/notes/pwa-ios/); [WebKit bug 215884](https://bugs.webkit.org/show_bug.cgi?id=215884); [Apple Developer Forums thread](https://developer.apple.com/forums/thread/788518)). The mitigations are architectural and cheap: make the scan screen one persistent route that drives "next pick" with state rather than URL changes, keep a single `MediaStream` mounted across picks, and test on current iOS before launch. A Capacitor shell with the ML Kit barcode plugin becomes necessary only if that proves unacceptable or the owner wants iOS haptics or NFC badges ([Capawesome ML Kit plugin](https://capawesome.io/plugins/mlkit/barcode-scanning)). Two ERP-specific prerequisites come first: `vercel.json` must stop sending `Permissions-Policy: camera=()` on the picking routes, and the app needs a manifest, service worker and an IndexedDB outbox, none of which exist (`vercel.json`; `public/`).

Scanning has a free baseline and a paid hedge. The browser-native `BarcodeDetector` is unusable cross-platform: caniuse lists it as disabled by default on every Safari and iOS version from 17.0 through 27.x and unsupported in Firefox, and reports say it broke on iOS 18 even with the flag on ([caniuse BarcodeDetector](https://caniuse.com/mdn-api_barcodedetector); [WebKit bug 281848](https://bugs.webkit.org/show_bug.cgi?id=281848)). The maintained open-source option is the `barcode-detector` ponyfill, which implements the same W3C API on ZXing-C++ compiled to WebAssembly (`zxing-wasm`, reader build about 1 MiB, loaded lazily on first scan), covers Code 128, UPC/EAN, QR and Data Matrix, and lets the WASM be self-hosted for offline and CSP ([Sec-ant/barcode-detector](https://github.com/Sec-ant/barcode-detector); [Sec-ant/zxing-wasm](https://github.com/Sec-ant/zxing-wasm)). The once-popular `html5-qrcode` has been in maintenance mode since April 2023 and should not be chosen ([Scanbot comparison](https://scanbot.io/blog/popular-open-source-javascript-barcode-scanners/)). Commercial engines decode blurry or glossy codes better (Dynamsoft's own benchmark shows zxing-wasm at 67% recall against its 85%, a vendor number to discount but directionally plausible), and STRICH's Basic tier is **€99/month** for unlimited devices and a soft 10,000 scans a month with a 14-day trial ([Dynamsoft benchmark](https://www.dynamsoft.com/codepool/benchmark-barcode-reading-javascript-zxing-wasm-dynamsoft-barcode-reader.html); [STRICH pricing](https://strich.io/)). The sensible gate is to ship the ponyfill behind a one-function adapter (`onScan(code)`), run a bake-off with thirty real SKUs under warehouse lighting against the STRICH trial, and keep whichever reads glass packaging reliably. Since the ERP controls location and tote labels, those should be printed large with generous quiet zones so the camera reads them instantly; product UPCs are the hard case.

For heavy use the fastest path needs no camera at all. Bluetooth HID "keyboard wedge" scanners type the barcode into whatever input is focused and work with any web app on iOS and Android with no SDK: Inateck handhelds sell for about **$70**, Socket Mobile's DuraScan D700 and S740 for about **$312 and $365**, while Zebra RS5100 ring scanners run roughly **$800-$1,400** and ProGlove MARK wearables around **$1,500** and are hard to justify for this team ([Inateck listing](https://www.desertcart.tw/products/253709545-bcst-70.md); [Socket S740 listing](https://www.lttpartners.com/products/socketscan-reg-s740-1d-2d-imager-barcode-scanner-blue); [Zebra RS5100](https://bechtle.com/ch-en/shop/zebra-rs5100-ring-scanner-bluetooth-5-2--4707629--p); [ProGlove MARK Basic](https://www.posmarket.com.au/products/barcode-scanners/wearable/proglove/mark-basic_20018.html)). The one real iOS trap is that a paired HID scanner hides the on-screen keyboard, so every picking screen must be operable without typing: big quantity steppers, reason chips, a camera-scan fallback button ([ShipHero on iOS keyboard](https://software-help.shiphero.com/hc/en-us/articles/4419362414733)). Rugged Android handhelds (Chainway at roughly **$270-$370**, Zebra TC22 around **$900-$1,400**) only make sense if personal phones fail in practice ([Chainway/Zebra listings](https://electronics.alibaba.com/product/zebra-tc26); [Zebra TC22](https://www.pbtech.co.nz/product/POSZBR5749919/Zebra-WLMT0-T22B8CBD8-A6-TC22-WLAN-Wifi-6-SE55-6in)). Feedback must be audio-first: ShipStation's own Scan to Verify gives audio and visual feedback, iOS has no vibration API and the checkbox-switch haptic trick is reported patched in 26.5, so the app should unlock Web Audio on the first tap and play distinct tones for right item, wrong item, wrong location and done, with full-screen green/red flashes as the visual channel ([Verify & Print](https://help.shipstation.com/hc/en-us/articles/360031021831-Verify-Print-Shipments-with-Barcode-Scan); [WebHaptics browser support](https://www.mintlify.com/lochie/web-haptics/advanced/browser-support)).

The picking model should be pull-based, waveless cluster picking into one tote per order. Order picking consumes up to 60% of warehouse labor and travel is about half of picking time, which is why batching and routing dominate the literature ([Roodbergen](https://www.roodbergen.com/warehouse/background.php); [Dukic & Oluic 2007](https://www.inderscience.com/filter.php?aid=13214)). De Koster and colleagues found that even simple batching significantly beats first-come-first-served single-order picking and that simple seed algorithms are the right choice when transparency and CPU time matter; Petersen and Aase found batching gave the largest savings of all policies tested, especially with small orders, which describes Freeze Pipe's one-to-five-line orders exactly ([de Koster et al. 1999](https://repub.eur.nl/pub/11852); [Petersen & Aase 2004](https://www.iaorifors.com/paper/47394)). Gallien and Weber's study of wave versus continuous release favored continuous release for e-commerce and found its main drawback, sorter gridlock, only applies to automated sorters Freeze Pipe does not have ([Gallien & Weber 2010](https://pubsonline.informs.org/doi/10.1287/msom.1100.0291)). Cluster picking (one picker, one pass, a cart with one tote per order) needs no conveyors, removes the sort step at pack, and its single real risk, placing an item in the wrong tote, is exactly what a tote scan eliminates ([Racklify cluster picking](https://racklify.com/encyclopedia/cluster-picking-benefits-and-drawbacks-when-to-use-it-in-fulfillment/)). The concrete design: when a picker taps "Start cart", a Deno edge function builds the best batch from the current pool of `awaiting_shipment` orders (priority by expedite, carrier cutoff, then age), seeds with the highest-priority order, repeatedly adds the order with the smallest marginal route cost until the cart's tote slots or weight limit are full or the marginal cost exceeds walking that order alone, claims those orders with `SELECT … FOR UPDATE SKIP LOCKED`, writes the batch, tote slots and ordered pick tasks in one transaction, and applies ERP-PICKING tags in the background. Single-line orders skip totes and go in a shared pile matched to orders at pack by scanning, Veeqo's "pick to pile" rule when more than half the batch is single-line ([Veeqo digital picking](https://help.veeqo.com/en/articles/8306650-digital-picking-overview)). Cart profiles (slots, slot volume, max weight, a fragile flag for glass) are settings, not constants.

Routing comes in two layers so the first one ships early. The baseline is the `pick_sequence` column: sort each cart's tasks by it and the picker walks a serpentine S-shape at zero compute, offline, on printed slips, and as the fallback if the solver ever fails. The second layer models the floor as a graph (aisle points, cross-aisle nodes, depot, pack station, edges with cost and optional one-way or blocked state), precomputes a shortest-path distance matrix between pick faces, and solves the open path from cart staging to pack station exactly with Held-Karp dynamic programming for up to about twelve stops (milliseconds in TypeScript) and nearest-neighbor plus 2-opt/Or-opt above that, capped at about 50 ms. Ratliff and Rosenthal proved single-block rectangular warehouse routing is a solvable special case of the traveling-salesman problem, and the standard heuristics (S-shape, largest gap, combined) exist precisely because exact routing was once expensive; at Freeze Pipe's list sizes it is not ([Roodbergen](https://www.roodbergen.com/warehouse/background.php); [Petersen 1997](https://iaorifors.com/paper/23908)). Supabase supports pgRouting, whose `pgr_dijkstraCostMatrix` feeds `pgr_TSP`, so the matrix can be built in the database, but a 300-node graph is small enough for a shared TypeScript module that runs in both the edge function and the browser, which matters because the phone must re-sequence the remaining stops locally whenever the picker skips, deviates or shorts, never forcing a walk back ([Supabase pgRouting](https://supabase.com/docs/guides/database/extensions/pgrouting.md); [pgRouting cost matrix](https://docs.pgrouting.org/3.4/en/pgr_dijkstraCostMatrix.html)). Google OR-Tools has no maintained official JavaScript binding and is not needed ([google/or-tools](https://github.com/google/or-tools)). Shelf height is a per-pick service-time penalty in batching and slotting, not a distance in routing, since the stop happens regardless.

The picking screen converges across ShipHero, Veeqo and Logiwa on one card: the location as the hero in readable parts (AISLE 3 / BAY 5 / LEVEL 2), product image and name (critical for look-alike glass), quantity as a large number, the target tote as a letter and color chip, progress ("3 of 12"), a two-stop preview, and a quiet "can't find / skip" action ([ShipHero iOS guide](https://software-help.shiphero.com/hc/en-us/articles/8497107616269-User-Guide-to-the-ShipHero-iOS-Mobile-App); [Veeqo digital picking](https://help.veeqo.com/en/articles/8306650-digital-picking-overview); [Logiwa pick to location](https://intercom.help/mylogiwa/en/articles/7033169-pick-to-location)). The confirmation sequence is scan location (a toggle, default on), scan item, scan tote; a wrong scan is a red flash, an error tone and no state change. Exceptions follow the synthesis of Seko, fulfillmenttools and Oracle flows: "skip" moves the line to the end and re-solves; "short" records the found quantity, creates a cycle-count task for that bin and flags the tote; "damaged" writes off and flags; a "hospital" tote state at pack shows red and never blocks the rest of the cart ([Seko WMS](https://seko.atlassian.net/wiki/x/hBF0qQ); [fulfillmenttools picking](https://docs.fulfillmenttools.com/documentation/apps/store-operations-app-beta/beta-picking-android-app); [Oracle pick confirm](https://docs.oracle.com/en/cloud/saas/supply-chain-and-manufacturing/26a/famml/pick-confirm.html)). Every scan is a timestamped row, which is how per-picker KPIs come free after launch; the baseline should be measured for two to four weeks before go-live from the current packing-slip flow (orders and lines per labor hour, mis-pick rate, short rate, percent shipped by cutoff) so the owner has Freeze Pipe's own numbers instead of vendor percentages.

Live state and offline tolerance need two pieces the ERP lacks. Supabase Realtime (there is no `supabase.channel` call anywhere in `src/` today) should drive the cart board, tote states and manager views, with the documented caveats that backgrounded phones throttle timers and drop the socket silently, so the client uses the Web Worker heartbeat option, a `heartbeatCallback` to reconnect, and a full re-fetch on `visibilitychange` because missed events are not replayed ([Supabase Realtime troubleshooting](https://supabase.com/docs/guides/troubleshooting/realtime-handling-silent-disconnections-in-backgrounded-applications-592794)). Because iOS has no background sync, offline is an in-app IndexedDB outbox of pick events with client-generated UUIDs, optimistic local state, and idempotent server RPCs so a replay cannot double-pick ([firt.dev](https://firt.dev/notes/pwa-ios/)). The inventory effects of a pick are physical only: pick moves `qty` from the bin balance into the tote container; pack moves it from the tote to an outbound staging location; the ShipStation ship event (already consumed by the webhook) closes the movement and frees the tote. The SKU-level deduction continues to happen at `awaiting_shipment` through `rpc_apply_shipstation_sale`, unchanged. One existing gap becomes urgent: cancellations after deduction are not auto-credited today (an open owner decision noted in the integration runbook), and a cancellation that arrives while an order is on a cart must now also pull the units back from the tote to a bin, so the pick module needs a "return to stock" task and the reconcile job needs to call the RPC for cancelled orders (`docs/SHIPSTATION_INTEGRATION.md`; `supabase/migrations/20260921000001_shipstation_apply_once.sql`).

The pack station is a desk, not a phone. Phones cannot talk to USB scales or run print clients; WebHID is desktop Chrome only (Android support is planned for Chrome 157), iPhones cannot connect to USB, serial or HID devices at all, and PrintNode's client runs on Windows, macOS and Linux (including a Raspberry Pi) but not on phones ([blink-dev WebHID thread](https://groups.google.com/a/chromium.org/g/blink-dev/c/aEsVkIFFYPE/m/KcxvyOIcBQAJ); [Chrome Help](https://support.google.com/chrome/answer/12576972?hl=ja); [PrintNode pricing](https://www.printnode.com/en/pricing)). The ERP pack screen on a PC or tablet-plus-PC does scan tote → order appears; scan every item (mismatch is a hard block, quantity counted per scan, mirroring ShipStation's rule that an order is Verified only when all items scan); rule-based box suggestion from SKU dimensions and a fragile flag (3D bin-packing is not justified at this volume); weight from the USB scale; then the hand-off. In the first design the screen shows the order-number barcode, the packer scans it into ShipStation's Scan to Print, ShipStation Connect prints, and the existing SHIP_NOTIFY webhook closes the loop. In the second design the edge function re-fetches the order to confirm it is still `awaiting_shipment` with an unchanged `modifyDate`, buys the label through V2 as ZPL, posts it to PrintNode (Essential plan **$9/month** for 5,000 prints and three computers; Lite is free for 50 prints), and marks the pack complete ([PrintNode pricing](https://www.printnode.com/en/pricing); [V2 Create Labels](https://docs.shipstation.com/create-labels)). QZ Tray is the local-agent alternative for raw ZPL without a cloud service, at a one-time support fee of roughly **$599-$749** ([qz.io](https://qz.io/)). Tote and bin labels are generated in the browser with `bwip-js` (Code 128 and QR among 100+ symbologies, canvas or SVG output, actively released) and printed on a Rollo (about **$200**) or Zebra ZD421 (about **$370-$650**) with third-party direct-thermal stock at **$0.03-$0.06 per label** ([bwip-js](https://github.com/metafloor/bwip-js); [shippinglabel.co printers](https://shippinglabel.co/blog/best-thermal-label-printer-shipping); [CDW Zebra ZD421](https://www.cdw.ca/product/zebra-zd421d-label-printer-b-w-direct-thermal/6439301)).

## Light the cart first, the shelves later, and never make lights mandatory

The evidence for pick-to-light is strong but comes from the wrong size of warehouse. An MHI case study of a fashion-accessories distributor reports errors falling from **0.32% to 0.0013%** and pick rates rising from **171 to 350 lines per hour**; Delta Galil went from about 97% paper-pick accuracy with every order audited to 99.95% with under 7% audited and a 13-month payback ([MHI case study](https://og.mhi.org/downloads/industrygroups/solutions-community/casestudies/retail---pick-to-light.pdf); [MHL News](https://www.mhlnews.com/technology-automation/article/22039615/picking-up-the-piecessmartly)). Every source also says lights suit a relatively small number of high-velocity SKUs, and no small-warehouse case study or break-even threshold was found ([TechTarget](https://www.techtarget.com/searcherp/definition/pick-to-light); [MMH on pick-to-light's evolution](https://www.mmh.com/article/pick_to_lights_evolution)). The implication for Freeze Pipe is that scan-confirmed picking in phase 2 already captures most of the accuracy gain, lights mainly cut search time, and search time matters least for a small crew that knows a few hundred SKUs and most for new or seasonal staff and for the "which tote?" decision on a multi-order cart. That is why both SMB vendors that have shipped or announced lights put them on the cart's tote slots, not on shelves: ShipHero's kit is a cart-front shield with 26 LEDs, a battery pack and a QR placard, requiring a cart, a scanner and an iPad, and ShipStation's announced version lights "the LED device mounted on the corresponding tote slot of the picking cart" ([ShipHero pick-to-light help](https://software-help.shiphero.com/hc/en-us/articles/36575614089741-How-to-Use-ShipHero-s-Pick-to-Light); [ShipStation blog](https://www.shipstation.com/blog/warehouse-picking-packing/)). Cart-mounted and pack-wall lights are a recognized, cheaper middle ground for batch picking because they light a handful of positions instead of every bin ([Racklify types of pick-to-light](https://racklify.com/encyclopedia/types-of-pick-to-light-systems-and-when-to-use-them/)).

Three hardware families are drivable from the team's own software. The cheapest is an ESP32 running WLED, whose documented JSON/HTTP API sets individual LEDs or ranges inside a segment (`{"seg":{"i":[0,8,"FF0000"]}}`) with up to 1,200 LEDs per controller, MQTT and UDP realtime modes, and finished controller boxes sold retail so nothing needs soldering; the documented constraints are that individual-LED calls must be sent sequentially, brightness and on-state must be set in a separate earlier request, and payloads should stay under about 24 KB ([WLED JSON API](https://kno.wled.ge/interfaces/json-api/)). A 60-LED-per-meter strip in aluminum channel along a shelf edge or across a cart's tote slots, with 3-6 LEDs per position for visibility, costs on the order of a few hundred to roughly $1,000 per 100 positions in parts (an unsourced estimate to verify), with labor for cutting, mounting and power injection as the real cost and 2.4 GHz WiFi among metal racking as the main reliability risk, mitigated by Ethernet or PoE boards for fixed installs. The most SMB-friendly commercial option is Voodoo Robotics: a **$5,000 starter kit** of 10 battery-powered wireless displays and one router with REST API support, no per-device subscription, displays that run "a year or more" on two AAA cells, and a documented API in which the ERP POSTs `command`, `line1`-`line5`, `quantity`, `color`, `seconds` and a `nonce` to a device and receives an HTTP callback of `ack` (button pressed), `nack` (timed out) or `call` ([Voodoo pricing](https://voodoorobotics.com/pricing/); [Voodoo developer docs](https://developer.voodoorobotics.com/)). At about $500 per position it fits a 10-slot cart or pack wall, not hundreds of bins. The industrial option is Banner/Turck PTL110 modules at roughly **$186-$280 each** at distributors, speaking Modbus RTU over RS-485, which any Raspberry Pi with a USB adapter can drive without vendor middleware but which needs wired bus and 24 V power and exceeds $25,000 for 100 bins in hardware alone ([Powermatic PTL110](https://www.powermatic.net/part/banner/ptl110s-t-qp150/1875961); [Turck shop](https://shop.turck.de/en/lighting-and-indicators/pick-to-light/3807535)). A German vendor's 200-bin example puts wireless at about **€8,000** and wired at about **€55,000**, with electrical work 30-50% of wired totals ([ekko pick-to-light cost](https://www.ekko.io/en/wissen/pick-to-light-cost)). Electronic shelf labels are the wrong tool for the "light up now" signal: commercial ESL makers market LED flash for picking but publish no self-serve API, and the open-source OpenEPaperLink firmware delivers LED commands only at the tag's next check-in, a minimum of about 40 seconds ([OpenEPaperLink](https://github.com/OpenEPaperLink/OpenEPaperLink)). They remain a good future fit as static e-paper bin labels that refresh when slotting changes.

The software architecture is the same for all three and should be built once, in phase 2, as a dormant capability. Three tables (`light_devices`, `light_locations` mapping a bin or tote slot to a device, segment and LED range or a Voodoo device id, and `light_commands` with a nonce, color, picker and a status of queued, sent, lit, acked, expired or failed) sit in Supabase. For Voodoo, an edge function calls the vendor API with the key held in Supabase secrets (Voodoo warns the key must never reach browser code) and a second edge function receives the callback and updates the row by nonce ([Voodoo developer docs](https://developer.voodoorobotics.com/)). For WLED or Modbus, a small on-site bridge (a Raspberry Pi running a Node or Deno service) holds a Realtime subscription on `light_commands`, serializes requests per controller, writes `sent`/`lit` back and posts a heartbeat every few seconds; the ERP marks devices offline when the heartbeat is stale. Each concurrent picker gets a color shown on both the phone and the lights. The rule that keeps this safe is that the phone scan remains the only source of truth: a light is an accelerator, and if a command is not lit within a few seconds the phone simply continues with text and map guidance. LED controllers belong on an isolated VLAN or SSID with no inbound internet, and the bridge makes only outbound connections with a scoped credential. The first project should be the cart or a 10-30 cubby pack wall for the single-line pile, because the wall never moves and can be USB-powered, and because it removes the one decision scanning does not: which tote.

## Four phases, a short shopping list, and what each one costs

The roadmap below orders the work so that every phase is useful on its own and the owner can stop after any of them. Effort figures are this report's engineering judgment, not sourced facts, and assume one experienced full-stack developer familiar with the ERP's conventions (forward-only migrations, `rpc_*` envelopes, TanStack Query hooks, `RequireRole` routes) working with the owner on the floor.

## Decisions the owner must make, and the risks that come with them

Several choices cannot be made by the developer because they change policy, cost or how staff work. The table lists each with the recommendation and the consequence of getting it wrong.

| Decision | Options | Recommendation | Why it matters |
|---|---|---|---|
| Who owns inventory and picking | ERP-native; ShipStation Premium native; both | ERP-native, ShipStation Inventory off | ShipStation's picking needs its own inventory and exposes no pick state; two owners drift and double-deduct ([Pick Using Batches](https://help.shipstation.com/hc/en-us/articles/49132678007451-Pick-Using-Batches)) |
| When stock leaves the books | Keep deduction at `awaiting_shipment`; move to pick confirm; add reservations | Keep as is; add the physical layer and nightly reconciliation | Preserves the oversell policy and ledger-derived idempotency in `rpc_apply_shipstation_sale`; avoids touching the hash chain |
| Cancellations after deduction | Leave manual; auto-credit via reconcile; auto-credit plus return-to-stock task | Auto-credit and create a return-to-stock task | A cancelled order on a cart must physically go back to a bin; today nothing credits it (`docs/SHIPSTATION_INTEGRATION.md`) |
| Carton granularity | LPN label per carton; one record per identical group with a count | Per-carton LPN for reserve stock; loose units at pick faces | Only per-carton satisfies "every master carton has a location"; costs one label per carton at receipt |
| Label hand-off | ERP screen barcode into ShipStation Scan to Print; ERP buys labels via V2 | Scan to Print first, V2 labels after a test-account proof | Scan to Print has zero API risk; V2 label-to-order-closure and quota effects are unverified ([V2 Create Labels](https://docs.shipstation.com/create-labels)) |
| Scanning hardware | Camera only; Bluetooth HID; rugged Android | Camera for light use, 2-3 HID scanners for heavy use | iOS hides the keyboard with a paired scanner, so screens must be typing-free ([ShipHero help](https://software-help.shiphero.com/hc/en-us/articles/4419362414733)) |
| Camera engine | Free ponyfill; STRICH €99/month; Dynamsoft/Scandit by quote | Ponyfill, with a 30-SKU bake-off against STRICH's trial | Open-source recall is lower on blurry codes; glass packaging is the hard case ([Dynamsoft benchmark](https://www.dynamsoft.com/codepool/benchmark-barcode-reading-javascript-zxing-wasm-dynamsoft-barcode-reader.html)) |
| Location code format | Numeric aisle-bay-level-position; letters for zones | Zero-padded aisle-bay-level-position, separate `pick_sequence`, prefixed scan value | Mixed formats and text-sorting bugs are the most common vendor-documented gotcha ([Veeqo](https://help.veeqo.com/en/articles/8306650-digital-picking-overview); [Warehance](https://warehance.com/blog/smart-warehouse-setup-zoning-and-location-naming-that-works)) |
| First lighting project | Cart tote slots; pack wall; A-SKU shelves | Cart and pack wall with WLED; shelves only if search time is measured | Cart lights remove the "which tote" decision; shelf lights add least where staff know the SKUs |
| Who digitizes the building | Owner and staff with a tape measure; developer; contractor | Owner and staff, using the template editor | A week of measuring and labeling is the single biggest non-software task |

The risks worth monitoring have specific triggers. ShipStation V1 is deprecated with no removal date and a third-party claim of a roughly one-year sunset from April 2025 that has not materialized; the adapter module and a V2-based order ingest design on `/v2/shipments` with `modified_at_start` polling are the hedge ([V2 authentication](https://docs.shipstation.com/authentication); [1TeamSoftware](https://1teamsoftware.com/documentation/shipstation-shipping/using/shipstation-api-access-limited-to-gold-amp-scale-plans-effective-may-2025/)). A plan downgrade below Standard would silently cut API access ([ShipStation plans](https://help.shipstation.com/hc/en-us/articles/38800795536027-Learn-About-ShipStation-Subscription-Plans)). The ShipStation webhook subscription must be account-wide, not per store, or orders routed to the second Shopify store (id 383716) would arrive only via the poll ([Endless Commerce changelog](https://endlesscommerce.com/changelog/2026-08-02-shipstation-order-routing-and-notifications/); `supabase/migrations/20261013000001_sale_dashboards.sql`). iOS standalone camera instability is unconfirmed as fixed and must be tested on the exact phones staff carry before phase 2 ships ([WebKit bug 215884](https://bugs.webkit.org/show_bug.cgi?id=215884)). Supabase Realtime drops silently on backgrounded phones and the design must assume it ([Supabase troubleshooting](https://supabase.com/docs/guides/troubleshooting/realtime-handling-silent-disconnections-in-backgrounded-applications-592794)). The ERP's own conventions add two: any new `reference_type` such as `pick_task` needs a CHECK-constraint migration before a ledger row can cite it, and `CREATE OR REPLACE FUNCTION` does not validate referenced tables, so each new RPC needs a smoke call after deploy (`CLAUDE.md`; `supabase/migrations/20260504000001_baseline_schema_from_staging.sql`). Finally, the ROI of the map and of pick-to-light at this scale rests on no independent data; the only way to know is the baseline-versus-after measurement built into phase 0 and phase 2, which the owner should insist on.

## Conclusion

The research reframes the owner's question. The original framing treated ShipStation as a partner the module must stay "seamless" with; in practice ShipStation is a boundary, generous on the order and label sides and sealed on the picking side, and the module's viability depends on respecting that boundary rather than fighting it. Once the ERP owns the physical layer, "real time" stops being a ShipStation property and becomes a Supabase property, achieved with Realtime subscriptions and an idempotent outbox on the phone, with ShipStation touched only by background tags and one scan at the pack bench. The most consequential design choice is also the least visible: adding a physical balance ledger beside the existing SKU ledger, reconciled by one arithmetic identity every night, so the deliberate oversell policy and hash-chained audit trail the owner already paid for remain exactly as they are.

Two implications follow for sequencing. The map is not the glamorous phase; it is the foundation whose quality (consistent codes, correct `pick_sequence`, carton LPNs minted at receipt) determines whether the picker ever trusts the phone, so it deserves the unhurried week of measuring and labeling that no software can replace. And pick-to-light should be designed in on day one as a dormant table and a color-coded tote slot, then bought last, because scanning captures most of the accuracy gain and the cart is the only place at this scale where a light removes a decision the picker would otherwise have to make.

## Appendix A: Proposed schema additions (SQL sketch)

The sketch follows the ERP's conventions: forward-only migrations, `rpc_*` SECURITY DEFINER functions returning `{ok, error}` JSONB, RLS on every table, `row_version` and `updated_at` triggers on mutable tables, `chk_` constraint prefixes. Quantities are integers because glass units are discrete. The existing `locations` row for Main Warehouse remains the site; `wh_locations` is the bin hierarchy beneath it.

```sql
-- Layout and bins
create table wh_layouts (id uuid pk, site_location_id uuid references locations, name text,
  version int, width_mm int, depth_mm int, published_at timestamptz);
create table wh_rack_templates (id uuid pk, name text,
  kind text check (kind in ('shelving','pallet_rack','floor','bin_wall','cart','bench')),
  bays int, levels int, positions_per_level int, bay_width_mm int, depth_mm int,
  level_heights_mm int[], default_location_type text);
create table wh_racks (id uuid pk, layout_id uuid, template_id uuid, code text,
  aisle text, side text check (side in ('L','R')), x_mm int, y_mm int, rot_deg int,
  first_bay_no int, bay_direction int check (bay_direction in (1,-1)));
create table wh_locations (id uuid pk, site_location_id uuid references locations,
  parent_id uuid references wh_locations, path ltree,
  kind text check (kind in ('zone','aisle','rack','bay','level','bin','station')),
  code text unique, barcode_value text unique,
  location_type text check (location_type in ('pick_face','reserve','staging_inbound',
    'pack_station','outbound_staging','returns','quarantine','damaged','tote_slot')),
  is_pickable bool, is_sellable bool, pick_sequence int, rack_id uuid, bay int, level int, position int,
  x_mm int, y_mm int, z_mm int, width_mm int, depth_mm int, height_mm int,
  max_weight_g int, max_units int, max_containers int, velocity_class text, golden_zone bool,
  active bool default true, row_version int);
create index on wh_locations using gist (path);

-- Containers (license plates) and physical balances
create table containers (id uuid pk, lpn text unique,
  type text check (type in ('master_carton','inner','tote','pallet')),
  parent_container_id uuid, location_id uuid references wh_locations,
  status text check (status in ('open','sealed','consumed','in_use','free','hospital','shipped')),
  freight_shipment_id uuid, freight_carton_group_id uuid, created_at timestamptz);
create table container_contents (container_id uuid, sku_id uuid, qty int, primary key (container_id, sku_id));
create table inventory_balances (sku_id uuid, location_id uuid, container_id uuid,
  on_hand int not null default 0, allocated int not null default 0,
  available int generated always as (on_hand - allocated) stored,
  unique (sku_id, location_id, coalesce(container_id, '00000000-0000-0000-0000-000000000000')));
create table inventory_movements (id uuid pk, movement_group_id uuid, ts timestamptz,
  performed_by uuid references profiles, sku_id uuid, qty_delta int,
  type text check (type in ('receive','putaway','move','case_break','pick','pack','ship',
    'adjust','count','replenish','return')),
  location_id uuid, container_id uuid, ref_type text, ref_id uuid, device_id text);
-- insert-only via RLS and a block-mutation trigger, as inventory_transactions does today

-- Picking
create table sku_location_assignments (sku_id uuid, location_id uuid,
  role text check (role in ('primary_pick','secondary_pick')), min_qty int, max_qty int,
  replen_uom text check (replen_uom in ('each','inner','master_carton')), active bool);
create table pick_batches (id uuid pk, picker_id uuid, cart_profile_id uuid,
  status text check (status in ('building','picking','picked','packing','complete','cancelled')),
  started_at timestamptz, completed_at timestamptz);
create table pick_batch_orders (batch_id uuid, shipstation_order_id bigint, tote_container_id uuid,
  slot_no int, slot_color text, status text check (status in ('pending','picking','picked','short','hospital','packed')));
create table pick_tasks (id uuid pk, batch_id uuid, seq int, location_id uuid, sku_id uuid,
  shipstation_order_item_id bigint, qty_required int, qty_picked int default 0,
  tote_container_id uuid, status text check (status in ('pending','picked','short','skipped')),
  picked_at timestamptz);
create table pick_events (id uuid pk, client_event_id uuid unique, task_id uuid,
  kind text, scanned_value text, ts timestamptz, picker_id uuid); -- idempotent outbox target

-- Lights (dormant until phase 4)
create table light_devices (id uuid pk, type text check (type in ('wled','voodoo','modbus')),
  address text, last_seen_at timestamptz, firmware text);
create table light_locations (location_id uuid, device_id uuid, segment int, led_start int, led_end int,
  vendor_device_id text);
create table light_commands (id uuid pk, nonce text unique, location_id uuid, color text,
  picker_id uuid, status text check (status in ('queued','sent','lit','acked','expired','failed')),
  queued_at timestamptz, lit_at timestamptz, acked_at timestamptz);
```

Core RPCs: `rpc_putaway(container_or_sku, location, qty)`, `rpc_move_inventory`, `rpc_case_break`, `rpc_claim_pick_batch` (uses `FOR UPDATE SKIP LOCKED` on eligible `shipstation_orders`), `rpc_confirm_pick(client_event_id, task_id, scanned_value, tote)`, `rpc_short_pick`, `rpc_pack_verify`, `rpc_complete_pack`, `rpc_post_cycle_count`, `rpc_reconcile_physical_vs_rollup`. A migration must extend the `inventory_transactions.reference_type` CHECK allowlist with `pick_task` and `cycle_count_task` before those RPCs can cite them in the SKU-level ledger (only when a SKU total actually changes, such as a count variance).

Reconciliation identity (run nightly, surfaced in Settings → Change Log): for each SKU, `sum(inventory_balances.on_hand where location is pickable, reserve, outbound_staging or a tote) - sum(allocated to orders in awaiting_shipment that have not shipped) = inventory_levels.warehouse_finished`. Any variance creates a count task for the SKU's locations rather than silently adjusting either side.

## Appendix B: ShipStation integration sequence

Order intake stays on the existing webhook and reconcile functions with three changes: subscribe ORDER_NOTIFY and SHIP_NOTIFY account-wide (no `store_id`), tighten the reconcile poll on `modifyDateStart` to a 2-5 minute cadence with an overlap window and PST/PDT correction, and have the reconcile also call `rpc_apply_shipstation_sale` for `cancelled` orders so credits post and a return-to-stock task is created ([V1 Subscribe to Webhook](https://www.shipstation.com/docs/api/webhooks/subscribe/); [V1 List Orders](https://www.shipstation.com/docs/api/orders/list-orders/); [V1 requirements](https://www.shipstation.com/docs/api/requirements/)). Keys: `shipstation_order_id` (V1 `orderId`) for every write; `orderKey` plus `storeId` for Shopify cross-reference; `orderItemId` (and `lineItemKey`) for pick lines ([V1 OrderItem model](https://www.shipstation.com/docs/api/models/order-item/)).

Outbound signals are a queued worker respecting 40 requests per minute: on batch claim, `POST /orders/addtag {orderId, tagId}` with ERP-PICKING (optionally `POST /orders/holduntil`); on pick complete, swap to ERP-PICKED; on exception, add ERP-EXCEPTION; on pack complete under design A, nothing (the packer scans into ShipStation); under design B, re-fetch the order, abort if status or `modifyDate` changed, `POST /v2/labels/shipment/{shipment_id}` with `label_format: "zpl"` and `label_download_type: "inline"`, post to PrintNode, store `label_id`/`shipmentId`; if labels are ever bought outside the order context, `POST /orders/markasshipped` with `notifySalesChannel: true` ([V1 Add Tag](https://www.shipstation.com/docs/api/orders/add-tag/); [V2 Create Labels](https://docs.shipstation.com/create-labels); [V1 Mark as Shipped](https://www.shipstation.com/docs/api/orders/mark-as-shipped/)). Items to prove in a test account before design B: V2 label on the backing shipment closes the ShipStation order and notifies Shopify; API labels count toward plan quota; `GET /orders/{orderId}` path and `sortBy` enum values. All ShipStation calls live in one `_shared/shipstation-adapter.ts` so V1 removal is a single-file change.

## Appendix D: Glossary for the owner

A **bin** or **location** is one addressable shelf position with its own barcode. A **pick face** is the bin a picker takes units from; **reserve** is where unopened master cartons wait. An **LPN** (license plate number) is the barcode on one physical carton or tote that lets the system track that container as a unit. A **tote** is the bin on the cart that holds one order's items; **pick-to-tote** or **cluster picking** means one walk fills several totes for several orders. A **hospital tote** is one flagged with a problem (short, damaged) so packing does not stall. **Putaway** is moving received stock to its bin; a **case break** opens a master carton to feed the pick face; **replenishment** moves cartons from reserve to pick faces when they fall below a minimum. **Slotting** is deciding which SKU lives where; the **golden zone** is waist-to-shoulder height. **Waveless** picking builds the next cart whenever a picker is free instead of releasing orders in timed batches. **Put-to-light** lights the tote slot an item belongs in; **pick-to-light** lights the shelf bin to pick from. A **PWA** is a website installed to the phone's home screen that behaves like an app.
